# Research & Architectural Decisions: OmniStock MVP

## 1. Multi-Tenancy Strategy, Tenant Context Safety & Role Ownership
- **Decision**: PostgreSQL Row-Level Security (RLS) with Transaction-Scoped Context (`SET LOCAL`), `NULLIF` Empty-Context Handling, Strict Role Separation, and TypeORM.
- **Rationale**:
    - **RLS Policy Pattern**: Every tenant-owned table (all 17 tenant-owned tables: `users`, `audit_logs`, `customers`, `categories`, `products`, `warehouses`, `inventory_items`, `low_stock_alerts`, `stock_movements`, `stock_transfers`, `stock_transfer_items`, `orders`, `order_items`, `order_allocations`, `sync_webhook_credentials`, `sync_logs`, `sync_attempts`) enables and forces RLS and enforces tenant matching for the runtime role (`omnistock_app`):
      `ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;`
      `ALTER TABLE <table> FORCE ROW LEVEL SECURITY;`
      `CREATE POLICY <table>_tenant_isolation ON <table> FOR ALL TO omnistock_app USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid) WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);`
    - **Context Evaluation Semantics**:
        - **Unset setting**: `current_setting('app.current_tenant_id', true)` returns `NULL`, so `NULLIF(..., '')::uuid` evaluates to `NULL` (0 rows matched on reads; writes rejected).
        - **Empty setting (`''`)**: `NULLIF('', '')::uuid` evaluates to `NULL` (0 rows matched on reads; writes rejected), preventing UUID cast errors when pooled connections reset custom GUCs to `''`.
        - **Valid UUID**: Enforces strict `tenant_id` equality on both `USING` and `WITH CHECK`.
        - **Malformed UUID**: Fails closed with a PostgreSQL UUID cast error (`22P02 invalid_text_representation`); never grants access or broadens visibility.
    - **Transaction-Scoped Context (`SET LOCAL`)**: `TenantInterceptor` extracts `tenant_id` strictly from the authenticated server-side JWT context (never trusting client-supplied headers, query params, or payload fields) and sets `SET LOCAL app.current_tenant_id = '<tenant_uuid>'` inside the active database transaction.
    - **Why Session-Level `SET` Is Forbidden**: Session-level `SET` persists on the connection after a request completes. With connection pooling, subsequent requests reusing the same connection could inherit the prior request's tenant context. `SET LOCAL` guarantees automatic reset on `COMMIT` or `ROLLBACK`.
    - **Database Role Ownership & Privilege Separation**:
        1. **Migration / Admin Role (`omnistock_migrator`)**: Owns application schemas, tables, sequences, and triggers; executes version-controlled DDL migrations (`up`/`down`); is never used by normal application runtime requests.
        2. **Runtime Application Role (`omnistock_app`)**: Must not own any tenant tables or schemas (preventing `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` or `DROP POLICY`); created with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`; has zero DDL or policy-modification privileges; receives only required DML privileges (`SELECT, INSERT, UPDATE, DELETE` on mutable tenant tables, narrow `SELECT, INSERT, UPDATE` on the global `tenants` directory, and `SELECT, INSERT` only with `UPDATE, DELETE, TRUNCATE` revoked on append-only `stock_movements`, `audit_logs`, and `sync_attempts`).
- **Alternatives Considered**:
    - *Schema-per-tenant*: Higher operational overhead, complex migrations across hundreds of schemas, and harder cross-tenant operational maintenance.
    - *Application-level filtering (`WHERE tenant_id = ...`)*: Prone to developer omission and lacks database-level isolation guarantees.
    - *Prisma ORM*: Rejected in favor of TypeORM to align with NestJS dependency injection, explicit `QueryRunner` transaction scoping (`SET LOCAL`), and raw SQL migration control.

## 2. Concurrency Control & Database-Level Inventory Constraints
- **Decision**: Database-level Pessimistic Locking (`SELECT FOR UPDATE`) in Global Deterministic `(product_id ASC, warehouse_id ASC)` Order combined with explicit PostgreSQL `CHECK` constraints on `InventoryItem`.
- **Rationale**:
    - For state-transition mutations on `StockTransfer` (`dispatch`, `receive`, `cancel`), `Order` (`submit`, `allocate`, `ship`, `cancel`, `PATCH`), `User` (`PATCH /users/{id}` last-admin check), `Warehouse` (`PATCH /warehouses/{id}` deactivation check), or `SyncLog` (`claim`, `retry`), the transaction first acquires a pessimistic lock (`SELECT ... FOR UPDATE`) on the target row(s) before validating state, preventing concurrent duplicate requests from violating business invariants.
    - When allocating, reserving, transferring, shipping, cancelling, or adjusting stock, `SELECT FOR UPDATE` within the database transaction serializes concurrent mutations on the target `InventoryItem` rows, which are always locked in global deterministic `(product_id ASC, warehouse_id ASC)` order to prevent deadlocks across concurrent operations.
    - To guarantee database-level integrity independent of application code, `InventoryItem` enforces explicit PostgreSQL constraints: `CHECK (on_hand >= 0)`, `CHECK (reserved >= 0)`, `CHECK (reserved <= on_hand)`, `CHECK (in_transit >= 0)`, and `CHECK (low_stock_threshold IS NULL OR low_stock_threshold >= 0)`.
    - `available` is strictly a derived read-only quantity (`on_hand - reserved`) and is never independently writable; `in_transit` is never included in `on_hand` or `available`.
- **Alternatives Considered**:
    - *Optimistic Locking*: Good for low-contention, but inventory hot-spots (e.g., flash sales) would result in many retries/failures.
    - *Application-only validation*: Insufficient under race conditions or direct SQL/service bugs.

## 3. Inventory Traceability (Immutable `StockMovement` Ledger & Reserved `RETURN` Enum — `F2-2`)
- **Decision**: Authoritative Database-Level Protection (`BEFORE UPDATE OR DELETE` Trigger + Role Privilege Restrictions) with Transactional Application Repository Safeguards and Reserved `RETURN` Enum Value in MVP.
- **Rationale**:
    - **Authoritative Database Enforcement**: `StockMovement` is an append-only ledger owned by `omnistock_migrator`. PostgreSQL enforces immutability via a `BEFORE UPDATE OR DELETE` trigger (`prevent_stock_movement_mutation()`) that unconditionally raises an exception on any attempt to modify or delete an existing ledger row. In addition, the runtime database role (`omnistock_app`) is granted only `SELECT` and `INSERT` privileges on `stock_movements` (`UPDATE, DELETE, TRUNCATE` are revoked).
    - **Application-Level Safeguards & Reserved `RETURN` Value (`F2-2`)**: Every physical (`on_hand`) stock quantity change in the MVP (manual adjustment `ADJUSTMENT`, order shipment `SALE`, transfer dispatch/receipt `TRANSFER`) executes inside an atomic database transaction that updates `InventoryItem`, inserts the corresponding `StockMovement` record, and evaluates `LowStockAlert` state. The `StockMovement.type` enum (`ADJUSTMENT | SALE | TRANSFER | RETURN`) preserves `RETURN` as a **reserved enum value** not yet supported by a public return workflow in the MVP; no endpoint creates a `RETURN` movement in the MVP, and any future return workflow must update inventory and evaluate low-stock alerts transactionally.
- **Alternatives Considered**:
    - *Application-level repository hook alone*: Rejected as the sole enforcement mechanism because direct SQL queries, bulk updates, or repository bypasses could mutate or delete historical ledger records without database-level protection.

## 4. Automatic Warehouse Allocation, Priority Ordering & Split Allocation (`OrderAllocation`)
- **Decision**: Global Deterministic `(product_id ASC, warehouse_id ASC)` Database Lock Acquisition Followed by In-Memory Priority-Ordered Evaluation (`priority ASC, created_at ASC, id ASC`), Dedicated `OrderAllocation` Entity, and All-or-Nothing Atomic Reservation.
- **Rationale**:
    - **Two-Step Lock vs. Evaluation Order (Deadlock Prevention)**:
        1. Identify all candidate `InventoryItem` rows across active warehouses (`Warehouse.is_active = true`) for the requested order items.
        2. Acquire database row locks (`SELECT ... FOR UPDATE`) in global deterministic `(product_id ASC, warehouse_id ASC)` order so allocation never deadlocks with concurrent stock transfers, shipments, or manual adjustments.
        3. After locks are held, evaluate warehouse allocation preference in memory using `(Warehouse.priority ASC, Warehouse.created_at ASC, Warehouse.id ASC)` (`CHECK (priority >= 1)`, lower number = higher priority).
    - **Dedicated `OrderAllocation` Entity**: Replaces the deprecated single `OrderItem.allocated_warehouse_id` field. When a single warehouse cannot fulfill the full `OrderItem.quantity`, `AllocationService` splits the fulfillment across multiple active warehouses, creating one `OrderAllocation` row (`order_id`, `order_item_id`, `product_id`, `warehouse_id`, `allocated_quantity`) per contributing warehouse so that $\sum \text{allocated\_quantity} = \text{OrderItem.quantity}$.
    - **All-or-Nothing Reservation**: If total `available` stock across all active warehouses is insufficient for *any* line item in the order, the entire transaction rolls back (`ROLLBACK`), leaving zero partial reservations and rejecting the request with `409 Conflict` (`INSUFFICIENT_STOCK`).
- **Alternatives Considered**:
    - *Locking `InventoryItem` rows in warehouse priority order*: Rejected because concurrent stock transfers or adjustments lock in `(product_id ASC, warehouse_id ASC)` order and could deadlock against priority-ordered locks.
    - *Single `allocated_warehouse_id` on `OrderItem`*: Cannot represent split shipments without mutating/duplicating customer-facing `OrderItem` lines.
    - *Partial order reservation (`PENDING` with partial locks)*: Ties up inventory indefinitely on unfulfillable orders and contradicts `US3` Scenario 2.

## 5. Idempotent Synchronization, Three-Phase Transactions, Lease Recovery & Worker RLS (`F7-1`..`F7-6`, `A9`, `F10-1`)
- **Decision**: Three-Entity Synchronization Architecture — `SyncWebhookCredential` (HMAC-SHA256 Signing Credentials) + `SyncLog` (Logical Event Header, Lease Metadata & Retry State Machine) + `SyncAttempt` (Append-Only Attempt Execution History) Executed Across Three Explicit Transaction Phases (`Phase A Claim`, `Phase B Domain`, `Phase C Failure Persistence`) with RLS-Safe Per-Tenant Worker Polling.
- **Rationale**:
    - **Why Three Explicit Transaction Phases (`F7-1`)**:
        - In PostgreSQL, retryable errors such as deadlocks (`40P01`), serialization failures (`40001`), or lock/statement timeouts (`55P03`/`57014`) abort the active transaction block. If `SyncAttempt` insertion and `SyncLog` retry scheduling were attempted inside the same transaction as domain order/allocation execution, rolling back the aborted domain transaction would also destroy the failure diagnostic record.
        - Therefore, after initial webhook ingestion commits a new `SyncLog` as `PENDING` (`attempt_count = 0`), every execution attempt is separated into three explicit transaction phases:
            1. **Phase A — Claim Transaction**: Locks the `PENDING` or due `RETRY_SCHEDULED` `SyncLog` row (`SELECT ... FOR UPDATE` / `FOR UPDATE SKIP LOCKED`), increments `attempt_count = attempt_count + 1` (the **only** place `attempt_count` is ever incremented), transitions `status = 'PROCESSING'`, sets 60-second lease metadata (`processing_started_at = CURRENT_TIMESTAMP`, `lease_expires_at = CURRENT_TIMESTAMP + INTERVAL '60 seconds'`, `lease_token = gen_random_uuid()`, `active_trigger_source`), and **commits before domain processing begins**.
            2. **Phase B — Domain Transaction**: Opens a fresh transaction with `SET LOCAL app.current_tenant_id`, locks `SyncLog` (`SELECT ... FOR UPDATE`), verifies `status = 'PROCESSING'`, `lease_token = claimed_lease_token`, and `lease_expires_at > CURRENT_TIMESTAMP`, and runs `OrderService.create(..., auto_allocate = true)`. On success, inserts the `SUCCEEDED` `SyncAttempt` (`attempt_number = SyncLog.attempt_count`) and updates `SyncLog` to `status = 'SUCCEEDED'` (`order_id`, `completed_at`, clearing lease metadata) in the **same** transaction as the domain mutations. On failure, rolls back the entire Phase B transaction (`ROLLBACK`).
            3. **Phase C — Failure Persistence Transaction**: After Phase B has fully rolled back, opens a **fresh transaction** with `SET LOCAL app.current_tenant_id`, locks `SyncLog` (`SELECT ... FOR UPDATE`) verifying `status = 'PROCESSING'` and `lease_token = claimed_lease_token`, inserts the failed `SyncAttempt` (`attempt_number = SyncLog.attempt_count`, without incrementing `attempt_count`), and atomically updates `SyncLog` (`RETRY_SCHEDULED` with $\text{delay\_seconds} = \min(30 \times 2^{k - 1}, 3600)$ when `FAILED_RETRYABLE` and $k < 5$, or `FAILED_PERMANENT` with `MAX_RETRIES_EXHAUSTED` when $k = 5$ or on permanent business failure), clearing lease metadata.
    - **Canonical `attempt_count` & Strict Manual Retry Rules (`F7-2`, `F7-3`)**:
        - `SyncLog.attempt_count` starts at `0`, increments by `1` exclusively in Phase A when claimed, and is capped at `max_attempts = 5` across `WEBHOOK`, `AUTO_RETRY`, and `MANUAL_RETRY`.
        - `POST /sync/logs/{id}/retry` accelerates **only** `RETRY_SCHEDULED` events (`attempt_count < max_attempts`) by locking the row (`SELECT ... FOR UPDATE`) and setting `next_retry_at = CURRENT_TIMESTAMP` and `next_trigger_source = 'MANUAL_RETRY'` without executing domain logic in the HTTP request, without incrementing or resetting `attempt_count`, and without increasing `max_attempts`. `PENDING`, `PROCESSING`, `SUCCEEDED`, and `FAILED_PERMANENT` are rejected with `409 Conflict` (`INVALID_SYNC_RETRY_STATE`).
    - **Distinct Error Namespaces (`F7-4`)**:
        - Separate columns store `pg_sqlstate` (5-char PostgreSQL SQLSTATE only: `'40P01'`, `'55P03'`, `'57014'`, `'40001'`), `http_status` (HTTP status `100..599` only), `error_code` (canonical application slug only: `'DB_DEADLOCK'`, `'DB_LOCK_TIMEOUT'`, `'DB_QUERY_TIMEOUT'`, `'DB_SERIALIZATION_FAILURE'`, `'DB_TRANSIENT_UNAVAILABLE'`, `'PROCESSING_LEASE_EXPIRED'`, `'MAX_RETRIES_EXHAUSTED'`, `'INSUFFICIENT_STOCK'`, `'VALIDATION_ERROR'`, `'RESOURCE_NOT_FOUND'`, `'VARIANT_PARENT_NOT_SELLABLE'`), and sanitized `error_message` (never persisting secrets, credentials, headers, or sensitive payload data).
    - **Processing Lease Expiry & Crash Recovery (`F7-5`)**:
        - If a worker crashes while a `SyncLog` is in `PROCESSING`, the uncommitted Phase B domain transaction is rolled back by PostgreSQL. Once `lease_expires_at <= CURRENT_TIMESTAMP`, `SyncRetryWorker` reclaims the expired `PROCESSING` row via `SELECT ... FOR UPDATE SKIP LOCKED`, records a single `FAILED_RETRYABLE` `SyncAttempt` (`attempt_number = SyncLog.attempt_count`, `lease_token = SyncLog.lease_token`, `error_code = 'PROCESSING_LEASE_EXPIRED'`) without incrementing `attempt_count` and without mutating existing `SyncAttempt` rows, clears the lease metadata, and transitions `SyncLog` to `RETRY_SCHEDULED` (if `attempt_count < 5`) or `FAILED_PERMANENT` with `'MAX_RETRIES_EXHAUSTED'` (if `attempt_count == 5`).
    - **Worker Algorithm & RLS Compatibility (`F7-6`)**:
        - Because `sync_logs` enforces `FORCE ROW LEVEL SECURITY` under `omnistock_app` (`NOBYPASSRLS`), querying `sync_logs` globally before setting `app.current_tenant_id` would evaluate to `NULL` and return 0 rows. `SyncRetryWorker` therefore enumerates active `tenant_id` values from the global non-RLS `tenants` directory (`SELECT id FROM tenants WHERE is_active = true ORDER BY id ASC`) and, for each tenant, opens per-tenant transactions with `SET LOCAL app.current_tenant_id = '<tenant_id>'` before polling `sync_logs` with `FOR UPDATE SKIP LOCKED`.
- **Alternatives Considered**:
    - *Single transaction for claim, domain execution, and failure logging*: Aborted PostgreSQL transactions roll back `SyncAttempt` rows on deadlock/serialization errors.
    - *Global `sync_logs` worker poll with `BYPASSRLS`*: Violates Batch 1 non-owner `NOBYPASSRLS` runtime role security invariants.

## 6. Foundational Audit Logging, Pre-Auth Security Events & Version-Controlled Migrations
- **Decision**: Distinct Append-Only Foundational `AuditLog` Entity/Service (Phase 2), Narrowly Scoped `SECURITY DEFINER` Function for Unattributable Pre-Auth Events, and Explicit SQL TypeORM Migrations (`synchronize: false`).
- **Rationale**:
    - **Separation of `AuditLog` and `StockMovement`**: `StockMovement` is strictly the immutable quantitative inventory ledger, whereas `AuditLog` records security and critical business events.
    - **Tenant-Scoped `AuditLog` Access**: Direct runtime queries/inserts on `audit_logs` by `omnistock_app` are governed by `audit_logs_tenant_isolation` (`USING` and `WITH CHECK` on `tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid`). Tenant-scoped requests can read and insert only rows matching the active tenant context, and can never read or directly insert `tenant_id IS NULL` rows.
    - **Unattributable Pre-Authentication Events (`tenant_id IS NULL`)**: When a login or token verification fails before a valid tenant can be attributed, the server-side auth handler calls a narrowly scoped PostgreSQL function `public.record_pre_auth_audit_log(p_action text, p_metadata jsonb)`:
        - Owned by a dedicated non-login role `omnistock_preauth_auditor` (`NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`) with `SECURITY DEFINER SET search_path = pg_catalog, public`.
        - `omnistock_preauth_auditor` is granted **only** `INSERT` on `public.audit_logs` (zero `SELECT`, `UPDATE`, `DELETE`, or access to any other table) and is governed by a dedicated `FOR INSERT TO omnistock_preauth_auditor WITH CHECK (tenant_id IS NULL AND actor_user_id IS NULL AND entity_type = 'Auth' AND action IN ('AUTH_LOGIN_FAILURE', 'AUTH_TOKEN_INVALID', 'SYNC_WEBHOOK_AUTH_FAILURE'))` policy.
        - `PUBLIC` execution is revoked (`REVOKE ALL ON FUNCTION public.record_pre_auth_audit_log(text, jsonb) FROM PUBLIC`); `EXECUTE` is granted only to `omnistock_app` and invoked strictly from internal server-side authentication error handling (never exposed via a public generic `AuditLog` endpoint).
    - **Append-Only `AuditLog` Protection**: Enforced at the database level via a `BEFORE UPDATE OR DELETE` trigger (`prevent_audit_log_mutation()`) plus revoking `UPDATE, DELETE, TRUNCATE` on `audit_logs` from `omnistock_app` and `omnistock_preauth_auditor`.
    - **Migration Safety**: All schema changes, roles, RLS policies, `CHECK` constraints, and immutability triggers are managed exclusively via explicit SQL TypeORM migrations (`up`/`down`), without depending on Phase 3–6 TypeORM entity classes.
- **Alternatives Considered**:
    - *Permissive RLS policy allowing `omnistock_app` to directly insert `tenant_id IS NULL` when tenant context is unset*: Rejected because any unscoped or misconfigured query path could write arbitrary `NULL`-tenant rows directly into `audit_logs`.

## 7. Catalog Modeling: Categories, Barcodes & Product Variants
- **Decision**: Flat Tenant-Scoped `Category` Entity + Unified SKU-Level `Product` Entity with Self-Referencing Parent-Variant Hierarchy (`parent_product_id` + `variant_attributes`).
- **Rationale**:
    - **Flat Categories**: `Category` (`categories`) is a tenant-owned table (`UNIQUE (tenant_id, lower(name))`) without nested `parent_id` hierarchy in the MVP. This satisfies category classification and filtering while avoiding recursive CTE complexity.
    - **Variants & Stock-Tracked Identity**:
        - Every `Product` row (including variant parent containers) has required `sku` (`NOT NULL`, `UNIQUE (tenant_id, sku)`), required `price` (`NOT NULL`, `CHECK (price >= 0)`), and an optional tenant-unique `barcode` (partial unique index `UNIQUE (tenant_id, barcode) WHERE barcode IS NOT NULL`).
        - A standalone product has `parent_product_id = NULL` and `is_variant_parent = false`.
        - A product with variants has a parent container row (`parent_product_id = NULL`, `is_variant_parent = true`, with its own base/catalog `sku` and `price`) and one or more child variant rows (`parent_product_id = <parent_id>`, `is_variant_parent = false`, `variant_attributes: JSONB` such as `{"size": "L", "color": "Blue"}`).
        - **How `InventoryItem` References Stock**: Stock is tracked strictly per sellable SKU (`Product.id` where `is_variant_parent = false`). Variant parent containers (`is_variant_parent = true`) are not sellable and cannot have `InventoryItem`, `StockMovement`, `StockTransferItem`, `OrderItem`, or `OrderAllocation` rows.
- **Alternatives Considered**:
    - *Separate `Product` and `ProductVariant` tables*: Requires every standalone product to create a dummy default variant row and forces multi-table joins across all inventory, movement, transfer, and order queries.
    - *Nested category trees*: Deferred beyond MVP per Constitution Principle IX (Simplicity).

## 8. Inter-Warehouse Stock Transfers & `IN_TRANSIT` Inventory Treatment
- **Decision**: Explicit `StockTransfer` & `StockTransferItem` Entities with `DRAFT -> IN_TRANSIT -> RECEIVED | CANCELLED` State Machine, Full-Only Receipt, Header-Row Pessimistic Locking, and Separate `InventoryItem.in_transit` Tracking.
- **Rationale**:
    - **In-Transit Accounting**: When a transfer is dispatched (`DRAFT -> IN_TRANSIT`), source warehouse `on_hand` is decremented immediately (recording a `StockMovement` with `type: TRANSFER`, `delta: -quantity`) and destination warehouse `InventoryItem.in_transit` is incremented by `quantity`. While `IN_TRANSIT`, those units are **not** in `on_hand` or `available` (`on_hand - reserved`) in either warehouse, preventing double-allocation.
    - **Full-Only Receipt Accounting**: Partial transfer receipt is not supported in MVP. When the destination warehouse confirms receipt (`IN_TRANSIT -> RECEIVED`), the full dispatched `quantity` for every `StockTransferItem` is received: destination `in_transit` is decremented by `quantity`, destination `on_hand` is incremented by `quantity`, and a destination `StockMovement` (`type: TRANSFER`, `delta: +quantity`) is recorded.
    - **Concurrency & Safety Constraints**: Dispatch, receive, and cancel operations lock the `StockTransfer` header row (`SELECT ... FOR UPDATE`) before checking `status` so concurrent duplicate requests cannot apply inventory mutations twice. `CHECK (source_warehouse_id <> destination_warehouse_id)` prevents same-warehouse transfers; composite `(tenant_id, warehouse_id)` foreign keys and RLS prevent cross-tenant transfers; only `DRAFT` transfers can be cancelled (`DRAFT -> CANCELLED`).
- **Alternatives Considered**:
    - *Single-step instant transfer*: Fails to model physical transit time and violates the `Incomplete Transfers` edge case requirement in `spec.md`.

## 9. Customer Management, Snapshots & Order Lifecycle State Machine
- **Decision**: Dedicated Tenant-Scoped `Customer` Entity with Order Snapshots and a 5-State Order Lifecycle (`DRAFT`, `PENDING`, `ALLOCATED`, `SHIPPED`, `CANCELLED`).
- **Rationale**:
    - **Customer Entity & Snapshots**: Orders reference `Customer` via `Order.customer_id` (`NOT NULL`, composite tenant FK) while storing `customer_name_snapshot` and `customer_email_snapshot` on `Order` so historical order records remain immutable if a customer later edits their profile. `Customer.email` and `Customer.phone` use tenant-scoped partial unique indexes (`WHERE email IS NOT NULL`, `WHERE phone IS NOT NULL`) so uniqueness is never enforced globally across tenants.
    - **Order State Machine & Ledger Timing**:
        - Every state-transition operation (`submit`, `allocate`, `ship`, `cancel`, `PATCH`) locks the `Order` header row (`SELECT ... FOR UPDATE`) before validating `Order.status` inside the same transaction.
        - `DRAFT` and `PENDING` hold no stock reservations.
        - `ALLOCATED` holds `InventoryItem.reserved` quantities backed by `OrderAllocation` rows; no `StockMovement` is written at reservation time because physical `on_hand` stock has not left the warehouse.
        - `SHIPPED` (`ALLOCATED -> SHIPPED`) atomically decrements both `on_hand` and `reserved` for each `OrderAllocation` and writes `SALE` `StockMovement` records (`delta: -allocated_quantity`).
        - `CANCELLED` is allowed from `DRAFT`, `PENDING`, or `ALLOCATED` (releasing `reserved` back to `available` when transitioning from `ALLOCATED`), and is strictly forbidden from `SHIPPED` (`409 Conflict` `INVALID_ORDER_TRANSITION`).
- **Alternatives Considered**:
    - *Bare `customer_name` string on `Order`*: Prevents customer reuse, order history lookup by customer, and CRM validation required by MVP scope.
    - *Writing `StockMovement` on reservation (`ALLOCATED`)*: Confuses logical reservation (`reserved`) with physical stock deduction (`on_hand`).

## 10. Low-Stock Alerts & Historical Preservation (`F2`, `F2-1`, `F3-3`)
- **Decision**: Per-Warehouse-SKU Threshold (`InventoryItem.low_stock_threshold`) Evaluated Against `available` (`on_hand - reserved`) with Persistent `LowStockAlert` Entity (`OPEN | RESOLVED`), Partial Unique Index Preventing Duplicate Active Alerts, and `ON DELETE RESTRICT` Referential Integrity.
- **Rationale**:
    - **Why Per-Warehouse-SKU Scope**: Different warehouses require independent reorder points for the same SKU. Storing `low_stock_threshold` (`INTEGER NULLABLE`, `CHECK (low_stock_threshold IS NULL OR low_stock_threshold >= 0)`) directly on `InventoryItem` allows each `(tenant_id, product_id, warehouse_id)` to opt in or out (`NULL` = disabled).
    - **Why Evaluate Against `available` (`on_hand - reserved`)**: If `on_hand = 20` and `reserved = 18`, only `2` units remain sellable for new orders (`available = 2`). Evaluating against `on_hand` would hide stockout risk until physical shipment occurs.
    - **Deduplication & Permanent Historical Retention (`F2-1`, `F3-3`)**: A partial unique index `CREATE UNIQUE INDEX uq_low_stock_alerts_open ON low_stock_alerts (tenant_id, inventory_item_id) WHERE status = 'OPEN'` guarantees at the database level that at most one `OPEN` alert exists per `InventoryItem`. Further stock reductions while already `OPEN` update `current_available` on the existing row; recovery (`available > low_stock_threshold` or `low_stock_threshold IS NULL`) sets `status = 'RESOLVED'` and `resolved_at = CURRENT_TIMESTAMP`, preserving the row permanently. To guarantee that resolved alert history can never be destroyed by cascading deletion, `low_stock_alerts` enforces `ON DELETE RESTRICT` on its composite foreign key to `inventory_items` (matching `Product` and `Warehouse` `ON DELETE RESTRICT`). Deactivating a `Product` or `Warehouse` never deletes, mutates, or resolves existing `LowStockAlert` rows.
    - **In-App MVP Scope**: Alerts are surfaced via `GET /alerts/low-stock` and `GET /dashboard/summary` without external email/SMS/push dependencies.
- **Alternatives Considered**:
    - *`ON DELETE CASCADE` on `low_stock_alerts -> inventory_items`*: Rejected because deleting an `InventoryItem` would silently destroy historical `RESOLVED` alert records.
    - *Stateless computed query (`WHERE available <= low_stock_threshold`) without `LowStockAlert` table*: Cannot record `triggered_at`, `resolved_at`, historical resolved alerts, or audit trail transitions.

## 11. Operational Dashboard & Basic Reporting (`F3`, `F3-1`, `F3-2`, `F3-3`)
- **Decision**: Single Read-Optimized Tenant-Scoped `DashboardService` (`GET /dashboard/summary`) with Gross Order Value Semantics (`period_order_value`), Strict UTC-Offset ISO-8601 Date Filtering across Aggregates and Recent Lists, Active-Only Inventory/Alert Summaries, and Explicit Exclusion of Inventory Cost Valuation.
- **Rationale**:
    - **Gross Order Value Terminology (`F3-1`)**: Because OmniStock MVP does not process payments, refunds, or accounting revenue recognition (`OUT-001`), order monetary summaries are named `period_order_value` (`allocated_order_value`, `shipped_order_value`, `combined_committed_order_value`) and explicitly defined as gross order value (`SUM(Order.total_amount)`), never collected payments, recognized accounting revenue, profit, or COGS.
    - **Date Input & Recent List Scoping (`F3-2`)**: `from` and `to` require full ISO-8601 timestamps with an explicit UTC offset (`Z` or `±HH:MM`, normalized to UTC; date-only strings or missing offsets are rejected with `400 VALIDATION_ERROR`). Inclusive UTC boundaries `[from, to]` apply consistently to `orders_by_status`, `period_order_value`, `recent_orders`, and `recent_stock_movements` (ordered by `created_at DESC, id DESC`).
    - **Active-Record Filtering (`F3-3`)**: `total_products` (`is_variant_parent = false AND is_active = true`), `total_variant_parents` (`is_variant_parent = true AND is_active = true`), and `total_warehouses` (`is_active = true`) count active entities only, and both `inventory_quantity_summary` and `low_stock_alerts_count` aggregate rows belonging to active products (`Product.is_active = true`) in active warehouses (`Warehouse.is_active = true`) only.
    - **Why Inventory Cost Valuation Is Excluded**: The MVP `Product` model tracks only selling `price` and does not track purchase cost or FIFO/weighted-average COGS. Multiplying `price * on_hand` represents retail list value, not accounting inventory valuation, and is therefore excluded rather than mislabeled.
- **Alternatives Considered**:
    - *Separate OLAP / BI database*: Overkill for MVP scale (up to 10 warehouses and 100k SKUs per tenant).

## 12. Explicit Permission-Based RBAC, Database-Backed Role Resolution & Webhook HMAC Auth (`F10-1`, `F10-2`, `F10-3`)
- **Decision**: `PermissionsGuard` (`@RequirePermissions('<module>:<action>')`) as the Sole Authoritative RBAC Guard Evaluating Database-Loaded `User.role`, Transaction-Safe Last-Admin Protection (`409 LAST_ACTIVE_ADMIN_REQUIRED`), and `WebhookSignatureGuard` (HMAC-SHA256 with `SyncWebhookCredential`) for Inbound Webhooks.
- **Rationale**:
    - **Authoritative `PermissionsGuard` & DB-Loaded Role (`F10-2`, `F10-3`)**:
        1. `JwtAuthGuard` verifies JWT authenticity (`401 AUTH_UNAUTHORIZED`).
        2. `TenantInterceptor` extracts `tenant_id` and `user_id` from the verified JWT, executes `SET LOCAL app.current_tenant_id = '<tenant_uuid>'`, and loads the current `User` record from `users`. If the user is absent or `is_active = false`, access is rejected with `403 TENANT_MEMBERSHIP_REQUIRED`.
        3. `PermissionsGuard` is the **sole** authoritative RBAC guard (replacing coarse `RolesGuard` usage so controllers never mix `@Roles()` and `@RequirePermissions()`). It evaluates the current `User.role` loaded from the database by `TenantInterceptor` (never trusting stale JWT role claims) and denies access by default (`403 INSUFFICIENT_PERMISSIONS`) if required permission metadata is missing or not granted.
        4. `PATCH /users/{id}` locks active `ADMIN` user rows (`SELECT ... FOR UPDATE`) and rejects deactivating or demoting the last active `ADMIN` of a tenant with `409 Conflict` (`LAST_ACTIVE_ADMIN_REQUIRED`).
    - **Dedicated `WebhookSignatureGuard`, Versioned Keyring & `SyncWebhookCredential` (`F10-1`, `F7-CRYPTO-1`..`F7-CRYPTO-3`)**:
        - `POST /sync/webhook/{source}` is an external channel webhook route narrowly exempted from `JwtAuthGuard` and `PermissionsGuard` and protected by `WebhookSignatureGuard` with NestJS raw-body preservation (`rawBody: true`).
        - **Versioned Encryption Keyring & Rotation (`F7-CRYPTO-1`)**: Configured via `WEBHOOK_SECRET_ENCRYPTION_CURRENT_KEY_VERSION` (`INTEGER >= 1`) and `WEBHOOK_SECRET_ENCRYPTION_KEYS` (`<version>:<64-lowercase-hex-chars>,...`, never stored in PostgreSQL). At startup, every `hexKey` is explicitly validated against `/^[0-9a-f]{64}$/` **before** calling `Buffer.from(hexKey, 'hex')` and verified to decode into a 32-byte `Buffer` (`byteLength === 32`), and the current key version is verified to exist in the keyring (failing startup closed on any key failing `/^[0-9a-f]{64}$/`, missing current key, duplicate version, or wrong decoded byte length; never silently falling back to another key). New credentials encrypt under `WEBHOOK_SECRET_ENCRYPTION_CURRENT_KEY_VERSION`; decryption selects the key by `credential.encryption_key_version` (failing closed with `401 WEBHOOK_AUTH_UNAUTHORIZED` if a referenced historical key is absent). Safe rotation adds the new key to `WEBHOOK_SECRET_ENCRYPTION_KEYS`, updates `WEBHOOK_SECRET_ENCRYPTION_CURRENT_KEY_VERSION`, retains historical keys until all stored credentials referencing them are re-encrypted (`SyncCredentialService.reencryptCredentialsToCurrentKeyVersion()` with a fresh 12-byte CSPRNG nonce) or no active/retained credential references that version.
        - **Canonical Secret, AAD, Nonce & HMAC Verification (`F7-CRYPTO-2`, `F7-CRYPTO-3`)**: `POST /sync/credentials` generates 32 CSPRNG random bytes encoded as a 64-character lowercase hexadecimal string `webhook_secret` (returned **exactly once** in `201 Created`, never returning `signing_key_sha256`), stores `secret_hash` (`SHA-256(UTF8(webhook_secret))` 64-char hex fingerprint, never used as an HMAC key), and encrypts `Buffer.from(webhook_secret, 'utf8')` (the 64 UTF-8 bytes of the hex string, NOT the 32 decoded random bytes) with AES-256-GCM using a fresh 12-byte CSPRNG nonce (`encryption_iv`, 24-char lowercase hex, guarded by `UNIQUE (encryption_key_version, encryption_iv)` with fresh-nonce retry on collision), 16-byte `encryption_auth_tag` (32-char lowercase hex), and `AAD = UTF8("${tenant_id}:${lower(source)}:${encryption_key_version}")`, producing a 128-character lowercase hex `encrypted_secret` (`CHECK (encrypted_secret ~ '^[0-9a-f]{128}$')`). `WebhookSignatureGuard` decrypts `encrypted_secret` only in memory with the identical `AAD = UTF8("${tenant_id}:${lower(source)}:${encryption_key_version}")`, validates `X-Sync-Timestamp` within `±300s`, validates `X-Sync-Signature` against `^v1=[0-9a-f]{64}$`, computes `HMAC-SHA256(key = Buffer.from(webhook_secret, 'utf8'), message = Buffer.concat([Buffer.from(`${timestamp}.`, 'utf8'), req.rawBody]))` directly over the original `req.rawBody` `Buffer` (both sender and server use `Buffer.from(webhook_secret, 'utf8')` without hex-decoding or SHA-256 key derivation), verifies both 32-byte digest buffers have equal byte length, and compares them via `crypto.timingSafeEqual`.
- **Alternatives Considered**:
    - *Coarse role-only decorators (`@Roles('ADMIN', 'MANAGER')`)*: Rejected in favor of a single authoritative `PermissionsGuard`.
    - *Evaluating `role` from JWT claims without DB lookup*: Allows demoted or deactivated users to retain old privileges until token expiration.

## 13. Database Test Isolation, Runtime Role Enforcement & Startup Effective-Privilege Verification (`FR-019`, `FR-023`)
- **Decision**: Disjoint Per-Test/Per-Suite Tenant Isolation Under `omnistock_app`, Strict Separation of `omnistock_migrator` Credentials, `>= 32`-Byte JWT Secret Material Validation, and Startup Effective PostgreSQL Privilege Verification (`has_table_privilege()`, `has_schema_privilege()`, `pg_has_role()`).
- **Rationale**:
    - **Why Standard Test `TRUNCATE`/`DELETE` Fails Under `omnistock_app`**: `omnistock_app` is `NOBYPASSRLS` with zero `TRUNCATE` privileges, and `stock_movements`, `audit_logs`, and `sync_attempts` enforce `BEFORE UPDATE OR DELETE` immutability triggers. Granting `TRUNCATE` or `DELETE` to `omnistock_app` or running test assertions under `omnistock_migrator` would invalidate RLS and append-only security guarantees.
    - **Deterministic Test Isolation**: All runtime/HTTP/service assertions execute strictly over `omnistock_app`. Tests provision fresh, unique tenants (`Tenant A`, `Tenant B` with unique slugs/UUIDs) via `tests/helpers/` factories so each test operates in an isolated RLS partition while keeping all triggers and role restrictions active. `omnistock_migrator` is used only for running migrations and, when full suite-level reset is needed, resetting a dedicated isolated test database (`NODE_ENV === 'test'` and database name verified to end with `_test`). Automatic `SyncRetryWorker` timer polling is disabled during HTTP integration tests (`SYNC_WORKER_ENABLED=false`) in favor of deterministic manual ticks (`await syncRetryWorker.runTick()`).
    - **Why Username Inequality Is Insufficient at Startup**: Checking `DB_APP_USER !== DB_MIGRATOR_USER` does not prevent a misconfigured database where `omnistock_app` was granted membership in `omnistock_migrator`, `pg_read_all_data`, or `pg_write_all_data`, or granted `BYPASSRLS`, table ownership, or `UPDATE`/`DELETE`/`TRUNCATE` on append-only tables. Therefore, `DatabaseModule.onModuleInit()` queries `pg_roles`, `pg_auth_members`, `pg_class`, `pg_namespace`, `pg_has_role()`, `has_table_privilege()`, and `has_schema_privilege()` and fails startup closed if `current_user` (or any role granted to it) holds prohibited attributes (`rolsuper`, `rolbypassrls`, `rolcreatedb`, `rolcreaterole`), prohibited role memberships (`omnistock_migrator`, `omnistock_preauth_auditor`, `pg_read_all_data`, `pg_write_all_data`), schema/table ownership, `CREATE` on `public`, `UPDATE`/`DELETE`/`TRUNCATE`/`TRIGGER`/`REFERENCES` on append-only tables, or `TRUNCATE`/`TRIGGER` on any of the 18 application tables.
    - **JWT Secret Length vs. Cryptographic Entropy (`>= 32` UTF-8 Bytes)**: `JWT_SECRET` is validated at startup via `Buffer.byteLength(JWT_SECRET, 'utf8') >= 32` (after rejecting empty/whitespace-only and single-character-repeated strings). Crucially, `>= 32` UTF-8 bytes is a **byte-length requirement only** and does **not** prove sufficient cryptographic entropy, and a non-repeating-character check is a basic sanity check only (never an entropy guarantee). Production `JWT_SECRET` values (`NODE_ENV === 'production'`) MUST be generated using a cryptographically secure random number generator (CSPRNG) with at least 32 random bytes (e.g., `crypto.randomBytes(32).toString('hex')` or base64), and production startup fails closed on any missing, weak, known-placeholder, or invalid secret; development and test environments may use environment-specific secrets subject to the documented validation rules.
- **Alternatives Considered**:
    - *Disabling triggers or using `omnistock_migrator` in integration tests*: Masks real-world permission and RLS bugs.
    - *Checking only `information_schema.role_table_grants`*: Misses privileges inherited through role memberships (`pg_auth_members`) or `PUBLIC` grants; `has_table_privilege()` and `pg_has_role()` evaluate effective privileges.

## 14. Observability, Trusted Log Context, Health Probes & In-Flight Drain on Graceful Shutdown (`FR-021`, `FR-022`)
- **Decision**: Correlation ID Propagation (`X-Request-Id`), Structured JSON Logging with Authenticated-Only Context and Redaction, Zero-Tenant Health/Readiness Probes, and Explicit In-Flight HTTP & Worker Transaction Tracking Prior to `DataSource` Shutdown.
- **Rationale**:
    - **Trusted Log Context & Redaction**: Accepting client-supplied `tenant_id` or `user_id` headers into structured logs would allow log spoofing/forging during unauthenticated requests. Log context populates `tenant_id` and `user_id` exclusively after `TenantInterceptor`, `WebhookSignatureGuard`, or `SyncRetryWorker` validates the identity, and redacts all secret material (`password`, `password_hash`, JWTs, `Authorization`, `webhook_secret`, `encrypted_secret`, `secret_hash`, `WEBHOOK_SECRET_ENCRYPTION_KEYS`, `X-Sync-Signature`).
    - **Health & Readiness Probes**: `GET /health/live` checks process responsiveness without DB I/O; `GET /health/ready` runs `SELECT 1` on `omnistock_app` without querying tenant tables or setting `app.current_tenant_id`, and returns `503 not_ready` as soon as shutdown starts or DB connectivity fails, without exposing internal host/pool details.
    - **Preventing Premature `DataSource` Destruction & Complete Multi-Phase Worker Drain**: In NestJS, if TypeORM closes the `DataSource` pool during `onModuleDestroy`/`onApplicationShutdown` while an HTTP request or a multi-phase `SyncLog` job is between `Phase A`, `Phase B`, and `Phase C`, in-flight jobs fail mid-lifecycle or skip `Phase C` failure persistence. Each `SyncLog` processing job MUST be tracked as a **single continuous logical unit** across its entire multi-phase lifecycle — `Phase A.1 — Ingestion Transaction` (when applicable for inbound webhooks), `Phase A.2 — Claim Transaction`, `Phase B — Domain Transaction`, and `Phase C — Failure Transaction` — from initial processing until either `Phase B` commits `SUCCEEDED` or `Phase C` commits `RETRY_SCHEDULED` / `FAILED_PERMANENT`. **The in-flight job tracker must never be released at transaction boundaries between `Phase A`, `Phase B`, and `Phase C`**; it is released only once in an outer `finally` block after the complete multi-phase job finishes. During graceful shutdown (`beforeApplicationShutdown`), the application sets `isShuttingDown = true` (`GET /health/ready` -> `503`), immediately stops accepting new worker jobs/claims, awaits all currently tracked HTTP requests and complete multi-phase `SyncLog` jobs (including `Phase C` when `Phase B` fails) up to `SHUTDOWN_DRAIN_TIMEOUT_MS` (default `15000`ms), logs a structured timeout warning without silently treating unfinished jobs as completed if the timeout expires (relying on the 60-second `lease_expires_at` recovery for any row left in `PROCESSING`), and closes `DataSource.destroy()` in `onApplicationShutdown` only after the drain procedure finishes.
- **Alternatives Considered**:
    - *Relying on default NestJS shutdown without in-flight request/worker tracking*: Risks closing the DB pool while active Phase B or Phase C transactions are committing.

## 15. API Conventions & Two-Tier Pre-Auth / Post-HMAC Webhook Rate Limiting (`FR-020`)
- **Decision**: Canonical Error Envelope, Uniform Pagination (`page >= 1`, `limit 1..100`), Strict `ValidationPipe` (`whitelist: true`, `forbidNonWhitelisted: true`), and Two-Tier Webhook Rate Limiting (Pre-Auth IP/Source+IP Tier + Post-HMAC Verified Tenant+Source Tier).
- **Rationale**:
    - **Why Webhook Rate Limiting Must Be Two-Tier**: Before `WebhookSignatureGuard` completes HMAC-SHA256 verification, `X-Sync-Tenant-Slug` is an unauthenticated client-supplied header. Keying a pre-auth rate limiter on `X-Sync-Tenant-Slug` would allow an unauthenticated attacker to send forged requests with a victim tenant's slug and exhaust that tenant's webhook quota (`429 Too Many Requests` cross-tenant DoS). Conversely, relying solely on a single global IP limit could allow one noisy integration to throttle unrelated integrations sharing cloud egress IPs.
    - **Trusted Client IP (`client_ip`) Resolution & Two-Tier Solution**:
        - **Trusted Client IP Resolution Policy**: Rate limiting must never trust arbitrary client-supplied `X-Forwarded-For` headers. Forwarding headers (`X-Forwarded-For`) are honored **only** when the immediate connecting peer (`req.socket.remoteAddress`) matches an explicitly configured trusted proxy in `TRUSTED_PROXY_IPS` (default empty/disabled). When the immediate peer is not a trusted proxy, `X-Forwarded-For` is ignored and `req.socket.remoteAddress` is used directly. When the immediate peer is a trusted proxy, `client_ip` is resolved via a right-to-left trusted-proxy chain policy (selecting the first rightmost address in `X-Forwarded-For` not in `TRUSTED_PROXY_IPS`, falling back to `req.socket.remoteAddress` if absent/malformed) so clients cannot bypass rate limits by injecting fake `X-Forwarded-For` entries. This exact `client_ip` policy applies consistently to all IP-based rate limits (`POST /tenants`, `POST /auth/login`, and both pre-auth webhook limits).
        - **Tier 1 — Pre-Authentication Tier (before `WebhookSignatureGuard`)**: Never trusts `X-Sync-Tenant-Slug`; enforces a per-IP bucket (`webhook:preauth:ip:${client_ip}`) and a per-source+IP bucket (`webhook:preauth:source_ip:${lower(source)}:${client_ip}`) using the trusted `client_ip` resolution policy to absorb unauthenticated floods.
        - **Tier 2 — Post-HMAC Verification Tier (after `WebhookSignatureGuard` verifies HMAC)**: Enforces the per-tenant, per-source quota keyed strictly by the verified `tenant_id` and normalized `source` (`webhook:tenant:${verified_tenant_id}:${lower(source)}`).
- **Alternatives Considered**:
    - *Pre-auth rate limiting keyed by `X-Sync-Tenant-Slug`*: Vulnerable to unauthenticated cross-tenant quota exhaustion.
    - *IP-only webhook rate limiting*: Cannot isolate per-tenant webhook throughput when multiple tenants use the same SaaS channel provider (`salla`, `shopify`).

## 16. Backup, Role Bootstrap, Restore Verification & External Keyring Retention (`FR-023`)
- **Decision**: Separate Cluster Role Bootstrap & ACL Restoration from `pg_dump --format=custom --no-owner --no-acl`, External Keyring Retention for All Historical `encryption_key_version` Values, and Mandatory Isolated Restore Verification (`scripts/verify-restore.sql`).
- **Rationale**:
    - **Why Role Bootstrap Is Separate from `pg_dump --no-owner --no-acl`**: PostgreSQL roles (`omnistock_migrator`, `omnistock_app`, `omnistock_preauth_auditor`) are cluster-level objects not included in a single-database `pg_dump`, and `--no-owner --no-acl` strips ownership and `GRANT`/`REVOKE` statements so archives are portable across environments. Therefore, restoring a backup requires: (1) bootstrapping the three cluster roles (`docker/postgres/init-roles.sql`), (2) running `pg_restore --no-owner --no-acl --role=omnistock_migrator` into an isolated restore database so `omnistock_migrator` owns all restored objects, and (3) re-applying the `omnistock_preauth_auditor` function ownership and `omnistock_app` least-privilege grants (`T039`) before any application connects.
    - **External Keyring Retention**: `sync_webhook_credentials.encrypted_secret` rows are encrypted under specific `encryption_key_version` integers. Encryption keys are never stored in PostgreSQL or database backups; operators must retain every historical key version referenced in `sync_webhook_credentials` within external secret storage (`WEBHOOK_SECRET_ENCRYPTION_KEYS`) so restored credentials remain decryptable.
    - **Isolated Restore Verification Gate**: Before traffic cutover, `scripts/verify-restore.sql` verifies RLS (`relrowsecurity` and `relforcerowsecurity` on all 17 tenant-owned tables), all 3 append-only triggers, effective `omnistock_app` privileges (`has_table_privilege()`, `pg_has_role()`), and keyring version coverage.
- **Alternatives Considered**:
    - *Embedding `WEBHOOK_SECRET_ENCRYPTION_KEYS` inside database backups*: Violates cryptographic separation between ciphertext storage and master keys (`F7-CRYPTO-1`).
